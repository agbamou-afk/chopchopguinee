## Welcome email — how to produce SMTP evidence

The welcome mail is now the cheapest way to close the SMTP gate: it is the only
message a brand-new account receives.

**Trigger condition.** `AFTER INSERT` on `public.profiles` → `_dispatch_welcome_email`.
It fires only when the profile has a non-empty `email`, `account_status = 'active'`
and `deleted_at IS NULL`. Auto-confirm remains **ON**: no confirmation mail is
generated by GoTrue and email verification is **not** required to use the
account.

**Idempotency.** The trigger claims `public.welcome_email_dispatches`
(PK `user_id`, unique `message_key = welcome-v1-<userId>`) with
`ON CONFLICT DO NOTHING` before sending. One account can therefore receive at
most one welcome mail, forever. Accounts that existed before the migration are
pre-seeded as already-welcomed.

**Where to inspect status.**

| Signal | Where | Meaning |
|---|---|---|
| Claim + transport | `public.welcome_email_dispatches` (`http_request_id`, `error_message`) | trigger ran, request handed to `pg_net` |
| HTTP result | `net._http_response` for that `http_request_id` | `200 {"success":true,"queued":true}` = accepted |
| Queue → provider | `public.email_send_log` (`template_name = 'welcome'`) | `pending → sent`, or `dlq` / `bounced` |
| Overall health | `email_get_health()` / Ops Command Center | queue + domain state |

**How to run a fresh test.** Register a new account on the production web app
with a *real, monitored* mailbox (Gmail + Outlook + one mobile client). Do not
use a `@chopchop.test` or `@chopchopguinee.com` placeholder address — those
addresses do not exist and produce a permanent bounce, which proves provider
handoff but never inbox placement.

**Evidence to record** (per inbox): received yes/no, inbox vs spam, latency,
sender display name and From address, subject, mobile rendering at 390×844, CTA
resolves to `https://chopchopguinee.com`, exactly one copy received, and the
matching `email_send_log` row transition. Attach screenshots.
